PASS AND SHOT DETECTION: RESEARCH AND KAGGLE TRAINING PLAN
Research checked: 2026-10-01

PURPOSE
=======
This note recommends replacements for the current heuristic pass and shot
detectors, summarizes the best public datasets and Hugging Face models found,
and gives a Kaggle notebook procedure for training a player-aware event spotter.


WHAT THE CURRENT PIPELINE DOES (AND WHY IT HALLUCINATES)
========================================================
The current implementation is in ai_engine/stage6_event_detection/events.py.

Passes:
- Continuous possession assigns the nearest tracked player to the ball within
  a 4.5 m radius, with a short debounce window.
- A same-team change of holder is counted as a completed pass in
  detect_extended_match_events(). It is not first required to look like a kick.
- An opposing-team holder change is counted as an attempted pass/turnover.
- detect_passes_with_metadata() adds distance/time/speed filters, but team
  statistics use the separate extended-event counts. This creates two different
  definitions of a pass and lets possession jitter inflate attempts.
- A loose ball, rebound, tackle, bad ball location, identity switch, or missed
  holder interval can therefore create a fake pass or turnover.

Shots:
- detect_shots() looks for ball movement with shot-like speed and direction
  toward a goal, then applies geometry, future-trajectory, player-proximity,
  pass-interval, and cooldown rules.
- This is fragile when the ball detector switches to another object, the ball
  trajectory is interpolated across a long gap, pitch calibration jitters, or
  the broadcast cuts/replays. A geometrically plausible trajectory is not proof
  a player intentionally attempted a shot.
- xG is a separate task. The current estimate_shot_xg() uses a small feature
  set (distance, angle, header, open-play) and falls back to a hand formula if
  the local LightGBM model cannot load. xG quality cannot fix shot-event quality.

RECOMMENDATION
==============
Use a learned temporal action-spotting model for PASS/SHOT event anchors, then
use tracking and ball trajectories as corroborating evidence and for linking an
event to local player IDs. Keep post-processing conservative and confidence
gated. Do not let possession changes alone create pass attempts.

For this codebase, the best target is FOOTPASS / SoccerNet Player-Centric Ball
Action Spotting (SN-PCBAS-2026), with the official TAAD baseline as the first
model to train. It is a track-aware action detector and predicts event frame,
team, jersey number, and class. Its classes include Pass, Cross, Shot, Drive,
Header, Throw-in, Tackle, and Block. This closely matches the need to count
events and attribute them to a tracked player.

Why this over a hand-built mathematical classifier:
- The known failure is event semantics (was this player action actually a pass
  or shot?), not just estimating a smooth probability from already-correct
  candidate events.
- A gradient-boosted classifier over trajectory features can be a useful second
  model, but it still needs correctly labeled positive and hard-negative
  examples. Public event-only coordinate feeds do not provide synchronized
  broadcast-video frames for the SoccerNet matches.
- FOOTPASS gives frame-anchored player-action labels and tracks, so it supplies
  direct supervision for the event and actor together.

Important limitation: the FOOTPASS "Pass" label identifies the pass action and
acting player; it does not by itself provide a reliable receiver identity or
completed/failed outcome. Keep those as a separate association task: after a
high-confidence pass anchor, inspect subsequent ball control and tracked-player
team/identity evidence. If evidence is ambiguous, store outcome as unknown,
instead of forcing completed/failed.

Shots on/off target and goals are also distinct labels. FOOTPASS "Shot" gives
the attempted-shot anchor, while outcome should be estimated from ball path,
goal/keeper evidence, or its own labeled head. Do not call a shot a goal just
because an interpolated ball path crosses a goal-area region.


DATASETS: WHAT TO USE
====================

1) PRIMARY TRAINING DATA: SoccerNet SN-PCBAS-2026 / FOOTPASS
   Hugging Face: https://huggingface.co/datasets/SoccerNet/SN-PCBAS-2026
   Baselines: https://github.com/JeremieOchin/FOOTPASS

   - 54 complete matches from 2023-24, across five major European leagues and
     UEFA Champions League.
   - 48 train, 3 validation, 3 challenge/test matches; 102,992 annotated
     events in total.
   - Labels are anchored to a frame and include team, jersey, and action class.
   - Dataset reports 81.5% of events have visible boxes; classes are imbalanced
     (Pass 49.9%, Drive 39.0%, remaining classes together about 11%).
   - Synchronized videos, tracklets/bounding boxes, spatiotemporal data, team,
     jersey, and role information make this the best fit for player attribution.
   - Hugging Face requires signing in and accepting dataset conditions. The
     repository lists about 235 GB total, including Full HD videos. Use the
     352x640 video package for a Kaggle experiment, not Full HD.
   - The public FOOTPASS baseline repo supplies TAAD, TAAD+GNN, and TAAD+DST.
     TAAD uses an X3D-S video backbone and player tracklets. The documented
     environment is Python 3.11.5, PyTorch 2.1.0, torchvision 0.16.0,
     Albumentations 2.0.8, NumPy 1.26, OpenCV 4.11, Decord 0.6, h5py 3.14.
   - FOOTPASS labels/baseline code are CC BY-NC 4.0 per its repo; SoccerNet
     broadcast video is governed by the SoccerNet access terms and must not be
     redistributed. Check the currently displayed HF/data terms before use.

   2026 label definitions:
     Pass = a ball strike toward a teammate
     Cross = pass from wide area toward penalty area
     Shot = attempt on goal
     Drive = player carries ball after reception
     Header = intentional contact with head
     Throw-in = restart from sideline
     Tackle = legal dispossession
     Block = interception/block of an opponent action

2) COMPLEMENTARY EVENT-SPOTTING DATA: SoccerNet Ball Action Spotting (SN-BAS)
   Official overview: https://github.com/SoccerNet/sn-spotting
   HF 2024: https://huggingface.co/datasets/SoccerNet/SN-BAS-2024
   HF 2025: https://huggingface.co/datasets/SoccerNet/SN-BAS-2025

   - Dense temporal action labels include PASS and SHOT. The 2024/2025 task
     taxonomy has 12 classes (PASS, DRIVE, HEADER, HIGH PASS, OUT, CROSS,
     THROW IN, SHOT, BALL PLAYER BLOCK, PLAYER SUCCESSFUL TACKLE, FREE KICK,
     GOAL).
   - The SoccerNet challenge reports only 7 annotated games for these dense
     datasets (with 2 additional challenge games). It is small; combine it with
     the larger SoccerNet Action Spotting dataset when using the official
     T-DEED recipe. The older Action Spotting labels cover 500+ games but are
     sparse global events and do not label ordinary pass events.
   - Good for improving broad event spotting and adding hard negatives; it is
     weaker than FOOTPASS for identifying which player acted.

3) OPTIONAL MANUAL TARGET-DOMAIN DATA
   - Create an adjudicated evaluation set from several complete matches,
     including match 79. Mark event frame, event type, player/track ID when
     identifiable, and shot/pass outcome separately.
   - Split by whole match, never by random clips from the same match. If the
     SoccerNet match in question appears in any downloaded split, reserve it
     entirely for evaluation to prevent leakage.
   - Include hard negatives: ball rebounds, keeper saves/throws, clearances,
     crosses, throw-ins, tackles, loose-ball scrambles, camera cuts/replays,
     and simple player-holder changes that were not passes.
   - Start with 5-10 complete matches of hand-checked annotations for local
     fine-tuning/evaluation if they are available. One 20-minute clip alone is
     too little for a reliable general-purpose model.

4) STATS BOMB OPEN DATA: USE FOR XG, NOT VIDEO EVENT SPOTTING
   https://github.com/hudl/open-data
   - Provides JSON event feeds, shots, passes, outcomes, lineups, and some 360
     freeze frames for selected matches. Useful for a separate structured xG
     model and tactical analytics.
   - It is not synchronized to the SoccerNet broadcast footage and cannot by
     itself label which frame in a SoccerNet video contains a shot/pass.
   - Keep licenses/attribution requirements. If publishing derived analysis,
     cite StatsBomb as its repository requests.


HUGGING FACE MODELS FOUND
========================

A) Best ready-to-run PASS/SHOT spotter:
   OpenSportsLab/OSL-loc-snbas-2025-e2e
   https://huggingface.co/OpenSportsLab/OSL-loc-snbas-2025-e2e

   - Video-based localization model trained on SN-BAS 2025 at 224p.
   - 12 classes, including PASS and SHOT.
   - Model card reports tight mAP 47.98 and loose mAP 58.35 on its benchmark.
     These are event-spotting metrics, not pass completion accuracy, player ID
     accuracy, or a direct comparison with our current pipeline.
   - Uses OpenSportsLib LocalizationModel. The model card shows loading weights
     by HF model ID and running localization over an annotated test set.
   - It returns event times/classes, not our local passer/receiver IDs or
     pass-completion outcome. Use it as a strong inference baseline and/or a
     teacher/candidate generator, then associate with our tracks.
   - License shown: AGPL-3.0; the card says to contact the maintainers for
     commercial licensing. Check compatibility before adding it to deployment.

   Minimal inference shape (see the model card/OpenSportsLib for the exact
   model-specific config YAML and current API):
       from opensportslib.apis import LocalizationModel
       model = LocalizationModel(
           config="path/to/localization.yaml",
           weights="OpenSportsLab/OSL-loc-snbas-2025-e2e",
       )
       predictions = model.infer(video_path="match_segment.mp4")

B) Older pass-only reference:
   OpenSportsLab/OSL-loc-snbas-2023-e2e
   https://huggingface.co/OpenSportsLab/OSL-loc-snbas-2023-e2e
   - Only PASS and DRIVE classes; no SHOT class. Its card reports tight mAP
     71.48 / loose mAP 85.62 on its older two-class benchmark. Scores are not
     comparable with the 2025 12-class model. Useful for comparison, not the
     main replacement because it cannot detect shots.

C) FOOTPASS TAAD/GNN/DST checkpoints:
   - The official source provides training code and baseline prediction files.
     I did not find an official Hugging Face trained FOOTPASS checkpoint.
   - For actor-aware detection, train the official baseline from the HF data.
     Do not assume the OSL 2025 checkpoint can emit FOOTPASS player IDs.

D) Avoid general video-chat/VLM models as the primary event counter:
   - Prompted VLMs may be useful for reviewing difficult clips or assisting
     human annotation, but they do not provide reliable frame-level event
     recall/precision guarantees or player-track attribution by default.
   - Use a temporal spotting model and its benchmark metric for production
     counts; keep a person in the loop for uncertain events.


KAGGLE TRAINING RECIPE (RECOMMENDED: FOOTPASS TAAD BASELINE)
============================================================
Goal: train a temporal player-centric action spotter for Pass and Shot, while
retaining the other FOOTPASS classes so the model can reject common confounders.

Before starting:
- Create a Hugging Face account. Open SN-PCBAS-2026 and accept its gated
  conditions. Create a read token with dataset-read access.
- Create a Kaggle Notebook, enable Internet and a GPU accelerator. Use the
  Kaggle Secrets panel for HF_TOKEN; never paste a token in a notebook cell.
- Kaggle documents a 12-hour notebook session and 20 GB of auto-saved
  /kaggle/working output. The full HF dataset is about 235 GB, so do not fetch
  Full HD or save extracted videos/checkpoints into the output folder. Use the
  low-resolution 352x640 train/validation packages and Kaggle's ephemeral
  scratch disk for video files. Run `df -h` before download/extraction. Keep
  only logs and best checkpoints under /kaggle/working. If the low-resolution
  archive cannot fit scratch space, use a smaller, match-complete subset or a
  larger cloud VM; do not split a single match between train and validation.
- Check the FOOTPASS dataset and model licenses. The baseline repo states
  training data videos are access-restricted and not redistributable.

STEP 1 — Create the notebook and check hardware/runtime
------------------------------------------------------
In Kaggle Notebook settings select GPU and Internet. Then run:
    !python --version
    !nvidia-smi
    !df -h
    import torch
    print(torch.__version__, torch.cuda.is_available())

The FOOTPASS README documents Python 3.11.5 / PyTorch 2.1.0 / torchvision
0.16.0 for TAAD and TAAD+DST. Kaggle images may have a newer preinstalled
PyTorch/CUDA. Start by using the Kaggle-compatible torch/torchvision pair; if
the repo fails due an API incompatibility, create a compatible environment or
use the official OSL/T-DEED alternative. Do not blindly downgrade CUDA wheels.

STEP 2 — Install baseline code and modest dependencies
------------------------------------------------------
    %cd /kaggle/working
    !git clone https://github.com/JeremieOchin/FOOTPASS.git
    %cd /kaggle/working/FOOTPASS
    !pip install albumentations==2.0.8 decord==0.6 h5py==3.14 opencv-python==4.11.0.86

If installing a dependency changes Kaggle's torch/torchvision, restart the
session and verify both versions again. Skip torch_geometric for the first
TAAD baseline; GNN is a later experiment with extra CUDA-compatible packages.

STEP 3 — Authenticate to Hugging Face without exposing secrets
--------------------------------------------------------------
In Kaggle, add secret named HF_TOKEN, then retrieve it through Kaggle's secret
API (it is not generally exposed as an environment variable):
    from kaggle_secrets import UserSecretsClient
    from huggingface_hub import login
    secrets = UserSecretsClient()
    hf_token = secrets.get_secret("HF_TOKEN")
    login(token=hf_token, add_to_git_credential=False)

Confirm access by opening the dataset page while logged in. The repository is
gated: accept its conditions on the website first. If Kaggle cannot see the
secret in a notebook, enable the secret for that notebook in Kaggle settings.

STEP 4 — Download only the data needed for the first run
--------------------------------------------------------
Use the HF repository file listing to verify exact names before downloading.
The current listing includes tactical_data_TRAIN.zip,
tactical_data_VAL.zip, videos_352x640_TRAIN.zip, and
videos_352x640_VAL.zip. Do not download challenge labels or Full HD videos.

Example download cell; put large archives on ephemeral scratch, not
/kaggle/working:
    import os
    from huggingface_hub import hf_hub_download
    scratch = "/tmp/footpass_data"
    os.makedirs(scratch, exist_ok=True)
    files = [
        "tactical_data_TRAIN.zip",
        "tactical_data_VAL.zip",
        "videos_352x640_TRAIN.zip",
        "videos_352x640_VAL.zip",
    ]
    for name in files:
        hf_hub_download(
            repo_id="SoccerNet/SN-PCBAS-2026",
            repo_type="dataset",
            filename=name,
            local_dir=scratch,
        )

The video archive is large. The current HF listing provides a split-level
archive, not a per-match download, so a small match subset does not avoid the
initial archive download. If the low-resolution archives and extracted files
do not fit Kaggle scratch, use the ready-to-run OSL model for inference or run
FOOTPASS training on a machine with more disk. Do not put the HF token in shell
history or print it.

STEP 5 — Unpack into the layout expected by the official repository
-------------------------------------------------------------------
The FOOTPASS README says video archives belong under `videos/` and tactical
annotations under `data/`; see `data/where_to_find_the_data.txt` in the clone.
Inspect archive contents before extracting and preserve their internal folder
structure. Keep expanded data on scratch disk, not the 20 GB saved-output
directory. The video ZIPs use WinZip AES encryption (ZIP compression method
99); Python's built-in `zipfile` raises `RuntimeError: ... encrypted, password
required` and cannot decrypt AES even if `pwd=` is supplied. The archive
password is separate from HF_TOKEN and is provided through SoccerNet/FOOTPASS
dataset access after accepting the required terms. Store it as a Kaggle Secret
named SOCCERNET_ZIP_PASSWORD; never hard-code or print it. Install pyzipper:
    !pip -q install pyzipper

Then extract the ordinary tactical annotation ZIPs with `zipfile` and AES video
ZIPs with `pyzipper`:
    import os, zipfile, pyzipper
    from kaggle_secrets import UserSecretsClient
    secrets = UserSecretsClient()
    zip_password = secrets.get_secret("SOCCERNET_ZIP_PASSWORD").encode("utf-8")
    root = "/tmp/footpass_root"
    scratch = "/tmp/footpass_data"
    os.makedirs(os.path.join(root, "data"), exist_ok=True)
    os.makedirs(os.path.join(root, "videos"), exist_ok=True)
    for name in ["tactical_data_TRAIN.zip", "tactical_data_VAL.zip"]:
        with zipfile.ZipFile(os.path.join(scratch, name)) as z:
            z.extractall(os.path.join(root, "data"))
    for name in ["videos_352x640_TRAIN.zip", "videos_352x640_VAL.zip"]:
        with pyzipper.AESZipFile(os.path.join(scratch, name)) as z:
            z.setpassword(zip_password)
            z.extractall(os.path.join(root, "videos"))

If you see the same error, confirm the password came from the SoccerNet/FOOTPASS
video archive access process; the HF token only authorizes downloading and is
not the ZIP password. This is a layout template: first inspect `namelist()` and
the official README/data path notes. Avoid adding an extra nested `data/data/` or
`videos/videos/` directory if the archive already contains the expected root.
Run `find data videos -maxdepth 3 -type f | head` and confirm both splits have
video and annotation files before starting training.

STEP 6 — Train the official TAAD baseline
-----------------------------------------
The official training script is `train_TAAD_Baseline.py`. Its documented
options include batch size, epochs, accumulation, clip length, tracklet count,
confidence threshold, NMS window, and temporal tolerance. Begin with a smaller
Kaggle-friendly run and save checkpoints under /kaggle/working:
    !python train_TAAD_Baseline.py \
      --data_root /tmp/footpass_root \
      --run_path /kaggle/working/footpass_runs \
      --epochs 8 \
      --batch_size 2 \
      --accum_steps 4 \
      --num_workers 2 \
      --clip_length 50 \
      --nb_tracklets 4 \
      --conf_thresh 0.15 \
      --nms_window 15 \
      --delta 12

If video clips are pre-extracted at 352x640 but the baseline assumes a
different resolution or data layout, follow the repository's current config
and loader code; do not silently resize annotations without applying the same
scale to boxes. Reduce batch size first if CUDA runs out of memory. If one
Kaggle session cannot finish, save/resume from checkpoints and store the final
checkpoint as notebook output or upload it to a private HF model repository.

STEP 7 — Validate without leakage and tune thresholds
-----------------------------------------------------
- Use only the official three-match VAL split for model selection. Never tune
  confidence thresholds on the challenge/test set.
- Evaluate event precision, recall, and F1 at the official temporal tolerance
  (FOOTPASS uses +/-12 frames and reports F1 at a confidence threshold of 0.15).
- Report Pass and Shot separately, plus macro F1 and false positives per
  minute. Check missed events and false alarms by hard-negative type.
- Tune per-class confidence threshold and temporal NMS using validation only.
  Choose higher thresholds if false positives are more costly than misses.
- Save validation prediction JSON and model/config metadata with the weights.

STEP 8 — Add the optional FOOTPASS game-context model
----------------------------------------------------
After TAAD works, use its predictions over the full training set and follow
FOOTPASS instructions to train DST (Denoising Sequence Transduction) as a
second-stage sequence filter. DST is intended to clean up noisy frame-level
predictions using game-level tactical context. TAAD+GNN is another follow-up
for inter-player context, but requires torch_geometric. Do not start with both
extensions on Kaggle; verify the baseline and disk/runtime budget first.

STEP 9 — Evaluate our pipeline and integrate as two separate stages
------------------------------------------------------------------
1. Run a downloaded pretrained spotter or the trained TAAD model on match 79
   and other full matches that were not used in training.
2. Convert event timestamps/frames into this app's video frame index correctly
   (SoccerNet half/game IDs, video.ini offsets, and segment offsets matter).
3. Join the event actor's team/jersey to our per-frame track/identity records.
   If jersey matching is not confident, keep actor unknown rather than choosing
   the nearest player as fact.
4. For a Pass anchor, estimate receiver/completion from later ball/player
   control. Keep Pass attempt, completed pass, and interception as distinct
   fields. A possession change alone must not create another pass.
5. For a Shot anchor, estimate on-target/outcome separately. A Shot label is
   not a Goal. Use only observed ball detections for final goal evidence, and
   record uncertainty when the ball is occluded/interpolated.
6. Store model confidence and source per event. Keep a configurable abstain
   threshold and do not export low-confidence predictions as certain events.
7. Compare old and new predictions against hand-checked labels by match, not
   by the same training clips. Replace old stats only after precision/recall
   actually improve on held-out matches.


FASTER FIRST EXPERIMENT BEFORE TRAINING
=======================================
Run the Hugging Face OpenSportsLab 2025 localization model on the existing
20-minute match 79 segment first. It is the fastest way to see whether a
dedicated temporal model reduces the current obvious hallucinations without
waiting for full training. Review the model card for its localization YAML,
resolution, and OSL dependencies. Compare predictions to hand-labeled events.
Then train FOOTPASS TAAD if player attribution is important.

For a codebase-friendly pilot, manually label a few minutes across the halves
of several matches with: event type, frame, actor track ID, team, pass outcome,
shot outcome, and whether the ball was visibly detected/interpolated. Use this
small set to test the adapter and threshold policy; it is not enough to claim a
general model is trained.


OPTIONAL MATHEMATICAL MODEL FOR PASS OUTCOME / XG
===============================================
After a temporal spotter finds candidate events, fit separate calibrated
models on structured observations:

Pass-validity classifier:
- Candidate-window features: ball displacement/velocity, acceleration, ball
  detector confidence, interpolation flag/gap age, distance to nearest player,
  actor-to-ball distance, teammate/opponent proximity, holder confidence,
  track quality, pitch zone, and camera-cut flag.
- Labels: true pass, cross, shot, clearance, keeper distribution, deflection,
  tackle, loose ball, or no event. Include hard negatives from this clip's
  current false detections.
- Candidate model: LightGBM/CatBoost for a fast transparent baseline, then a
  small temporal network if sequence context improves held-out performance.
- Use a whole-match split, class weighting, calibrated probabilities, and an
  explicit `uncertain/abstain` operating region.

xG model:
- Train a separate shot-to-goal probability model on event-level shot data
  such as StatsBomb Open Data. Use shot location, angle, body part, play type,
  pressure/defender context, keeper position/freeze frame when available, and
  outcome. Evaluate calibration (Brier score/reliability curve) as well as
  discrimination (AUC). Do not treat an xG model as a shot detector.
